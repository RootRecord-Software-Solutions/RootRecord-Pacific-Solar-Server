Security

This page is the public shape of the security architecture. It describes boundaries and the standard of evidence. It does not publish addresses, host names, credentials, or private endpoints. There is no numeric security rating.

  1. Person
  2. Agent
  3. Boundary
  4. Control
  5. Execution
  6. Evidence
  7. Persisted state

Public visibility does not mean public control. A public page is not an operator console.

Access boundaries

People, agents, and services reach systems through a boundary that matches the work. Crossing a boundary is a deliberate step.

Verification

State is accepted when there is evidence for it. A claim, a commit, or a command is not that evidence by itself.

Evidence

Execution should leave a record that can be checked later: what was asked, what ran, and what the system reported back. The public form of that record is the status feed. It shows a reading when the feed has one.

Deployment distinction

Source and the running system are different facts. Shipping a change and proving the running system took that change are separate steps. A commit is not proof of deployment.

Operational controls

Important operations stay controllable by people. Agents can prepare work inside a bound. The control that performs it stays visible. A change should remain understandable after it lands: what it was for, where it applies, and how someone can tell whether it took effect.

Continuity

Security includes being able to operate and repair the system without starting from zero. History, context, and evidence are part of that. Security material belongs in the RootRecord Library. Private material stays there. Knowledge · About

Public / private boundary

The public site may describe architecture, public telemetry, public status, and public documentation. It does not describe private addresses, private names, credentials, or internal paths. If a detail is not clearly public, it is left out. Status
